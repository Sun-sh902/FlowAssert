# Phase 3A architecture — Gate 1, before implementation

Authorized scope: five reviewed offline synthetic cases, Python evaluator, local SQLite, local CLI, additive GETs. No frontend development or Phase 3B. The accepted `app.main`/`Catalog` execution remains separate from the archive. `app.history_api` composes the existing app with three history GETs and a separate contract document. The original OpenAPI and provider contract remain byte-identical. No HTTP writer is exposed.

SQLite is sufficient for one local writer and bounded synthetic records. Use private directories (0700), files (0600), rollback journal DELETE, synchronous FULL, foreign_keys ON, busy_timeout, and explicit transactions. Read requests use mode=ro/query_only and one consistent read transaction. CLI alone creates/migrates the database; HTTP cannot initialize it. No claims of production multi-user durability or administrator security.

Publication invariants: canonical validated service bundle + pinned evaluator/research/contract/source identities; all ordered records and evidence references bound to the same original verification/snapshot; replayed result from the unmodified evaluator; required content present and digests correct. Source population remains the evaluator's nullable/boolean statement. Raw ticks and JSON missing/null/zero/false/empty distinctions survive canonical JSON storage without SQL coercion.

Archive state: ABSENT → BUILDING (inside an uncommitted transaction) → PUBLISHED. Failure or process death before COMMIT leaves ABSENT. Readers see only PUBLISHED. SQL triggers reject mutation/deletion and late child insertions; they complement read-time validation, not cryptographic immutability. Each archive stores the original full bundle, normalized ordered record/evidence rows, input identity, content seal, first publication clock, and original execution clock/snapshot. An archived snapshot is persistent and distinct from an ephemeral catalog snapshot.

Identity/idempotency: exact full candidate bytes including original execution timestamps/snapshot and provenance determine a SHA-256 identity. Exact retry reuses the ID only after validating stored equality and integrity. A new evaluator execution has a new receipt/snapshot and creates another archive. Changed evidence/evaluator/contract outside the five reviewed/pinned inputs is rejected as an explicit unsupported-source conflict. It cannot overwrite an archive. The default `seed` command is an atomic five-case ensure operation keyed by the reviewed source-set identity: retries do not re-execute an evaluator. Explicit `seed --reevaluate` replays all five and creates distinct evaluations. A crash rolls back the whole batch, including the seed-set registry.

Pagination: descending immutable autoincrement sequence, pinned maximum published sequence on the first list page; continue strictly below the last returned sequence. A new insert has a greater sequence and is excluded from that chain. No deletions are available. Signing binds database UUID, additive contract digest, endpoint kind, filter, limit, upper boundary and continuation boundary. Evidence cursors additionally bind history ID, persistent snapshot ID and payload mode; positions strictly advance. Keys persist across restart; cursors have no time expiry. Invalid scope → 400; explicit conflicting snapshot → 409; corrupt/inaccessible archive → 503. Cursors and snapshots of existing ephemeral APIs remain unchanged and separate.

Integrity: verify the accepted Python `json.dumps(sort_keys=True, separators=(',', ':'), ensure_ascii=True, allow_nan=False).encode('utf-8')` bytes and SHA-256; do not use JavaScript key/number ordering. Persist actual canonical bytes. Validate reference hashes, binding, schema and relational inventory on every read, even when payload is omitted. Available corrupt content blocks successful retrieval (503 INTEGRITY_FAILED); missing-at-evaluation content may be INTEGRITY_UNVERIFIABLE. Retrieval, internal content consistency, and external authenticity remain distinct. Database administrators who rewrite both content and local hash metadata can evade consistency checks; no external authenticity or tamper-proof storage is claimed.

Gate 1 challenge, design disposition: different evaluator identity is rejected; mid-write crash rolls back; foreign cursors rejected; inserts excluded by high water; wrong snapshot fails binding despite correct hash; post-publication mutation fails seal/invariants; unknown population stays null; historical cursor survives restart; default seed retries reuse first batch; old Detail route/model bytes stay unchanged except isolated evaluator path relocation. Gate 2 must exercise each disposition with real files/processes/HTTP and mutations.

## Final implementation calibration

The final implementation additionally stores the complete original five-case pending-publication snapshot basis, recomputes the accepted original snapshot digest and proves exact bundle membership. The published header seal includes the immutable SQLite sequence. These address correct-digest/wrong-snapshot and post-publication ordering mutation counterexamples; both have dedicated negative tests. Supported current state is `.runtime/delivery`; pre-final experimental stores are retained only as development evidence. Schema/API invariants above remain the implemented bounded contract. Final self-review and results are in PHASE3A_BACKEND_REPORT.md; this is not an independent audit or Owner Acceptance.
