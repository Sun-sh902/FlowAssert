## What this adds

The Action ran `flowassert-verify` on two CSV files. From 1.1.0 it also reads a source from a Google Sheets range, a
destination from HubSpot's contacts and either side from an `.xlsx` workbook, writes the records to resend, and adds a
run summary to the job's page. Every 1.0 input, output and default stays as it was; every new input is empty by
default, which means its option is not given.

## New inputs

| Input | Option |
| --- | --- |
| `source-sheet`, `source-range`, `source-timeout`, `skip-source-revision` | `--source-sheet`, `--source-range`, `--source-timeout`, `--skip-source-revision` |
| `destination-hubspot`, `destination-timeout` | `--destination-hubspot`, `--destination-timeout` |
| `source-format`, `source-worksheet`, `destination-format`, `destination-worksheet` | The workbook options ([the Excel note](1.1-excel.md)) |
| `export-dir` | `--export-dir` ([the exports note](1.1-exports.md)) |
| `summary` | `"true"` (default) adds the run summary below; `"false"` writes no job summary at all |
| `summary-keys` | `"false"` (default); `"true"` lists the keys of the records that are not Verified, up to 50, in the run summary |

`source` and `destination` are no longer marked required, since a sheet or HubSpot can stand in for them; the checker
still refuses a check with neither, with its own message. GitHub only warns about a missing required input **[unconfirmed]**, so
this changes nothing for an existing workflow.

A new output, `export-dir`, is the directory's path when files were written, and empty otherwise.

## Credentials

Credentials never pass through an input: an input's value can appear in the log of the step that sets it, and inputs
are not masked. The connectors already read theirs from the environment only (`FLOWASSERT_SHEETS_TOKEN` or
`FLOWASSERT_SHEETS_API_KEY`, and `FLOWASSERT_HUBSPOT_TOKEN`). A workflow sets them from repository secrets in the `env:`
of the step that uses the Action:

```yaml
- uses: Sun-sh902/FlowAssert@v1.1.0
  env:
    FLOWASSERT_SHEETS_TOKEN: ${{ secrets.FLOWASSERT_SHEETS_TOKEN }}
    FLOWASSERT_HUBSPOT_TOKEN: ${{ secrets.FLOWASSERT_HUBSPOT_TOKEN }}
  with:
    source-sheet: ${{ vars.LEADS_SPREADSHEET_ID }}
    source-range: Leads!A1:F
    destination-hubspot: contacts
```

GitHub documents passing a secret to an action "as an environment variable" on its step **[doc]**; that the variables
of the step reach the steps of a composite action is not stated in the pages read **[unconfirmed]**, and was not run.
`run_action.py` hands the checker its whole environment, as in 1.0, and never reads, prints, stores or summarises a
credential. A test runs the Action with a credential against the local fakes and requires that it appears in none of:
the step's printed output, its outputs file, the job summary, the reports and the exported files.

## The run summary

`$GITHUB_STEP_SUMMARY` holds GitHub-flavoured Markdown **[doc]**. 1.0's summary stays as it was (the state, the exit
status and whether the step passed, the checker's printed summary, and the premises table). After it, `summary: true`
adds:

```markdown
### What this run shows

**Mismatch.** No claim is made: the result is not Verified.

| Verified | Mismatch | Unverified | Source rows | Expected total |
| --- | --- | --- | --- | --- |
| 1 | 3 | 0 | 4 | 4 |

| Premise | Stated | Applied |
| --- | --- | --- |
| source_complete | yes | applied |
| destination_complete | yes | not applied: the stated total differs from the rows read |
| source_count | none | not stated |
| destination_count | 7 | differs from the rows read |

| Input | Read as | SHA-256 |
| --- | --- | --- |
| Source | file | `9f2c…` (full digest) |
| Destination | worksheet of an .xlsx workbook | `51aa…` (canonical form), file `0b7e…` |

Records to resend, in exports/: missing-from-destination.csv 3 rows.

This run is a new observation; it does not change any earlier report.
```

With scope `exact`, a line after the counts gives the destination-only records: `Destination-only records (scope
exact): Mismatch 1, Unverified 0.` The run summary is written only when the check concluded; a refusal keeps 1.0's job
summary alone. `summary` and `summary-keys` take only `"true"` or `"false"`; another value is refused like any other
boolean input, and that refusal is summarised.

- **No value, by default no key.** The run summary holds the verdict, the claim or "No claim is made", the counts,
  each premise with what was stated and whether it was applied, the inputs' kinds and digests, and the export files'
  names and row counts. It holds no key, unless `summary-keys: true`, and never a compared value. (1.0's `show-records:
  true` still puts the checker's record lines, which hold values, into 1.0's part of the summary: that is what it was
  documented to do, and its description keeps saying so.)
- **The applied column** uses the HTML report's words, from the JSON report: "applied", "not applied: the stated total
  differs from the rows read", "not stated", "matches the rows read", "differs from the rows read".
- **Size.** GitHub limits a step's summary to 1 MiB; beyond it the upload fails with an error annotation, and the step's
  result is unaffected **[doc]**. The run summary is a few kilobytes; with 50 keys it can grow, so each key is cut to
  200 characters (with `…`), and if the whole summary would pass 1,000,000 bytes, the checker's printed summary and the
  keys are replaced by one sentence that says they were left out because of the limit.
- The JSON report needed for the run summary is written to a temporary file in `RUNNER_TEMP` when `json` is not given,
  and removed afterwards.

## Scheduled checks

`examples/github-actions/` holds two workflows and a README:

- `scheduled-sheet-to-hubspot.yml`: `on.schedule` (`cron: "17 6 * * 1-5"`, at a minute other than the hour's first, as
  GitHub suggests, since jobs at the start of the hour may be delayed or dropped **[doc]**) and `workflow_dispatch`;
  credentials from secrets in `env:`; the JSON and HTML reports and the export directory uploaded with
  `actions/upload-artifact`. A scheduled run uses the default branch's latest commit, and in a public repository GitHub
  disables the schedule after 60 days without activity **[doc]**; the README says so.
- `workbooks.yml`: a check of two workbooks committed to the repository, on `push` and `pull_request`.

Each run writes new reports into a new folder named after `github.run_id`; nothing edits an old report.

## Tests

- `test_action.py`: every new input to its option; the run summary for every state, every premise and each kind of
  input; `summary: false`; `summary-keys`; the size rule; a sheet source and a HubSpot destination through the local
  fakes (`FLOWASSERT_SHEETS_TEST_ENDPOINT`, `FLOWASSERT_HUBSPOT_TEST_ENDPOINT`); workbooks; exports; the credential leak
  test.
- `.github/workflows/action-self-test.yml` runs the same through the Action itself on Linux, macOS and Windows: a
  workbook source whose records to resend must be byte for byte the command line's, and a check from a Google Sheets
  range to HubSpot against the fakes that `scripts/dev/serve_fakes.py` starts in the background of one step and
  leaves running for the next (it writes their loopback addresses to `$GITHUB_ENV`), with recognisable fake
  credentials that must appear in no output, report or exported file. That a background process started by one step
  of a job keeps running for its later steps, on all three systems, is not stated in the pages read **[unconfirmed]**:
  the workflow was not run. The same steps were walked through locally on macOS with `bash`, and `test_action.py`
  runs the same check in-process. `test_workflows.py` checks the workflow's structure, the pinned actions and the
  permissions, and also parses the example workflows, which may use only this Action at the CHANGELOG's latest
  version.
