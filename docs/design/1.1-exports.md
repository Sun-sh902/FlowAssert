## What an export is, and what it is not

After a check, a person wants to act: resend what did not arrive, correct what differs. An export writes, from the
check's own records, CSV files of the rows that need that action, each row exactly as it was read, under its file's own
header, so it can be imported again.

An export is advice. It never changes a record's state, a report, the summary of a command without the new options, or
the exit status. It is computed from the records the check concluded and adds no conclusion of its own, and it never
places a row whose state is unknown beside rows the check showed to be missing.

## The files

| File | Rows | Meaning, in one sentence |
| --- | --- | --- |
| `missing-from-destination.csv` | Source rows | The destination, stated complete, has no row with this key: these records did not arrive. |
| `values-differ.csv` | Source rows | The destination has one row with this key, and at least one compared field differs. |
| `duplicated-in-destination.csv` | Source rows | More than one destination row has this key: resending would add another; the destination needs merging. |
| `unknown-status-resending-may-create-duplicates.csv` | Source rows | The check could not conclude: the record may already be in the destination, so resending it may create a duplicate. |
| `only-in-destination.csv` | Destination rows | Scope `exact`, source population known: the destination has rows whose key is not in the source. |
| `only-in-destination-not-concluded.csv` | Destination rows | Scope `exact`, source population unknown: rows whose key is not among the source rows supplied, listed without a conclusion. |

A file is written only when it has at least one row. The names are fixed: they are part of the format, so a script can
rely on them.

## From a record to a file

Each source record is in exactly one file, or in none:

| Record | File |
| --- | --- |
| Verified | None |
| Mismatch, `existence` failed ("key not found in stated complete destination") | `missing-from-destination.csv` |
| Mismatch, `uniqueness` failed | `duplicated-in-destination.csv` |
| Mismatch, otherwise (a field rule failed) | `values-differ.csv` |
| Unverified or Pending, for any reason | `unknown-status-resending-may-create-duplicates.csv` |

The tests in this order are exhaustive: a failed `existence` leaves every field unknown, a failed `uniqueness` too ("no
arbitrary candidate selected"), so a Mismatch record falls in exactly one file. `existence` fails only when destination
coverage is sufficient (spec section 7), so **a destination that was not stated complete never yields a
`missing-from-destination.csv`**: its records without a destination row are Unverified, and go to the unknown file.

The unknown file holds every Unverified record: one whose key the destination may hold (coverage not established), one
whose source key is empty or repeated, one found with an empty value. They have one thing in common, which the name
says: the check did not show that they are absent, so resending them may create duplicates.

A destination-only record (scope `exact`) carries the destination rows with its key: every one of them, in destination
order, goes to `only-in-destination.csv` when its state is Mismatch and to `only-in-destination-not-concluded.csv` when
it is Unverified.

Rows keep their order: source rows by `source_row`, destination rows by their position in the destination.

## The bytes of a file

- **Encoding**: UTF-8 with a byte order mark (`EF BB BF`), so a spreadsheet program opening the file reads its
  characters correctly; FlowAssert's own CSV reader takes the mark as UTF-8's, not as part of the first column's name.
- **Header**: the row's own file's header, every column, in its order. For a workbook, row 1's texts; for a Google
  Sheets source, the range's first row; for a HubSpot destination, the property names read.
- **Rows**: every column of the row, as read: a CSV row's fields exactly, a worksheet row's cell texts ([the Excel
  note](1.1-excel.md#the-text-of-a-cell)), padded with empty strings to the header's width as the check reads them.
- **Line endings**: CR LF after every row, the last one included (RFC 4180).
- **Quoting**: a field is written in double quotes, with each `"` doubled, when it contains `,`, `"`, a carriage return
  or a line feed, or when it is the only field of its row and is empty (an empty line would be a blank line, which a
  reader skips). Every other field is written as it is.

So reading an exported file with `flowassert-verify`'s reader gives back the header and the rows exactly, and a test
requires it for every golden case.

## Text a spreadsheet would run as a formula

A field that begins with `=`, `+`, `-`, `@`, a tab or a carriage return may be run as a formula when a spreadsheet
program opens the file ("CSV injection"). Changing such text, for example by putting `'` before it, would change the
row: re-importing it into the destination would write the changed text, which is the very thing an export must not do.

**FlowAssert does not change exported text.** The files are for importing into the system the rows came from, where
the text is data, not for opening in a spreadsheet. It warns instead: the summary, the browser and the documentation
count the exported fields that begin with one of those characters, excluding plain numbers such as `-5` or `+44`
(`[+-]?[0-9]+([.][0-9]+)?`), and say to import the files rather than open them by double-clicking. This is a known
spreadsheet risk, stated where the files are offered.

## Reading the rows again

The check keeps only the compared columns of the source, never whole rows. An export needs whole rows, and knows which
only when the check is done. So the rows are read again:

- **A CSV file or a workbook** is read a second time with the same reader, and its digest must equal the first read's
  (the file's bytes for CSV, the canonical form for a workbook). A file that changed in between is refused, and nothing
  is exported or written.
- **A Google Sheets source** is not requested again: the rows are already in memory from the one read the check made.
- **A HubSpot destination** is not listed again. When an export is asked for with scope `exact`, the records listed are
  kept as they are read, so the destination-only rows can be written. They are only the properties read, and there
  are at most `--max-rows` of them, since the listing is refused beyond that (`--max-bytes` bounds each response, not
  the total). Without an export, or with scope `source`, nothing is kept.

## The command line

| Option | Meaning |
| --- | --- |
| `--export-dir DIR` | After the check, write the records to resend into the new directory `DIR` |

- `DIR` must not exist; FlowAssert creates it (one level), and writes each file with exclusive creation. A directory
  that exists is refused (`DIR: exists; --export-dir writes to a new directory`), so no export is mixed with an older
  one and nothing is overwritten. Each run is a new observation.
- **All or nothing**, like the reports (spec R10.12): the export files are written before the reports. If any cannot be
  written, or a file changed before it was read again, the files and the directory are removed, no report is written,
  and the check is refused. Otherwise the reports, the summary and the exit status are exactly those of the same
  command without `--export-dir`, followed by the lines below.
- **Refused** before any file is read: `--export-dir cannot be combined with --redact-values: the exported rows hold
  the values`. Redaction promises a report without values; an export of rows cannot keep that promise.

The summary, after the limitations line, which stays where it is:

```text
Records to resend, written to exports/ (advice from this check, not a further conclusion):
  missing-from-destination.csv: 3 rows
  unknown-status-resending-may-create-duplicates.csv: 12 rows; resending them may create duplicates
  2 exported fields begin with =, +, -, @, a tab or a carriage return: import the files rather than open them in a spreadsheet.
```

With nothing to export: `Records to resend: none; exports/ is empty.` A count of one uses `1 row` and `1 exported field
begins`. When the destination was not stated complete and some records were not found:
`  No missing-from-destination.csv: the destination was not stated complete, so absence is not established.`

## The packaged checker

`checkCsv` takes `exports: true` as an addition; without it, its result is exactly as before. With it, the result has
`exports`: an array with one member per file that has rows, in the order of the table above:

```js
{ file: "missing-from-destination.csv", rows: 3, meaning: "…", formulaFields: 0, text: "\ufeffexternal_id,phone\r\n…" }
```

`formulaFields` counts the file's fields that begin with a formula character, as the summary does. The summary of the
packaged checker does not change: there is no directory to name.

`text` is the file's text (its byte order mark as `\ufeff`), so that the n8n node and the browser write the same bytes
the command line writes. `exports` is `null` for a refused or failed check.

## The browser

Under the result, a section "Export records to fix":

- one entry per file that has rows: its name, its row count and its meaning in one sentence, all known from the report
  alone, and a download button;
- beside the unknown file's button, its warning: "The check could not conclude for these records. Some may already be
  in the destination; resending them may create duplicates.";
- when records were not found but the destination was not stated complete: "No list of missing records: the
  destination was not stated complete, so absence is not established.";
- once a file is built, when any of its fields begins with a formula character, the warning of the section above,
  with the count for that file.

Nothing is downloaded, and no file is read again, until a button is pressed. The file is built in the worker from the
file the person chose, read again and refused if its digest is not the one the check recorded; the page makes no
request. The worker keeps the built files until the next check starts. A report opened from the saved reports has no
export section: the files it came from are no longer there.

## The Action and the n8n node

The Action takes `export-dir`; its files can be uploaded as an artifact ([the Action note](1.1-action.md)). The n8n
node outputs the rows of each file as items on its own output, under the file's header, and attaches the files as
binary data ([the node note](1.1-n8n-node.md)).

## Tests

- Every golden case's exports, from Python and TypeScript, are byte for byte the same.
- Exporting changes no report, summary line or exit status: every golden case run with and without `--export-dir`.
- Re-import: each exported file read back with the check's own CSV reader gives the source rows exactly.
- Hostile values: quotes, line breaks inside values, a lone empty field, a byte order mark in a value, and
  formula-like text such as `=1+1`, `@SUM(A1)`, `-2+3`, kept exactly and counted.
- Refusals: an existing directory, `--redact-values`, a file changed between the two reads.
