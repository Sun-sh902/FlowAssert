## 什么变了，什么不能变

在 0.7.0 及以前，Worker 把每个文件整个读入（`File.arrayBuffer()`），解析它，再用 `crypto.subtle` 计算同一块缓冲区的摘要值。所以两个文件会同时留在内存里，另外还有核对本身要保存的内容。

从 1.0 起，Worker 通过 `File.stream()` 读取每个文件，手里只留着正在处理的那一块。

不能变的，是人或程序能看到的一切：记录、每条拒绝信息和它的行号、摘要值，以及两份报告的每个字节。命令行核对程序是参考。它用 `io.TextIOWrapper(newline="")` 读取，每次解码 8,192 字节，并且只在 CSV 读取器需要下一行时才解码。先遇到格式错误的行，还是先遇到无法解码的字节，取决于这个顺序；有两个核对样例专门检验它（`chunk-csv-error-before-later-decode-error`、`chunk-decode-error-in-first-chunk`）。

## 从文件到 8,192 字节的块

流给出的块有多大，由浏览器决定。读取器不依赖块的大小：

1. **流**的内容一次次读入同一块 1 MiB 的缓冲区（“自带缓冲区”的读取方式），所以读取文件时不会为每一块分配内存。浏览器的流不支持这种方式时，就使用浏览器给出的块。
2. **`ByteFeed`** 接收流的块，再交出恰好 8,192 字节的片段，最后一段可以短一些。片段完全落在一个块里时，它只是这个块的一个视图；片段跨两个块时，复制一次；缓冲区再次填充之前，块里剩下的不足一个片段的部分也复制一次。交出的每个字节都按文件顺序计入摘要值。
3. **`LineReader`** 只在手里没有完整的行时才要下一个片段，这正是 Python 的文本层再次读取的时刻。
4. `ByteFeed` 里攒够 8,192 字节时，取片段是同步的。只有 `ByteFeed` 空了而流还有内容时，读取器才等待（`await`）。所以不管流的块多大，解码器看到的都是同样的字节、同样的片段，时机也和以前一样；每个文件只等待几百次，不是每行一次。

打包的核对函数（`checkCsv`）拿到的文件是已经在内存里的字节。它把这些字节当作只有一块的流，通过同一个 `ByteFeed` 读取，所以读取器只有一个，不是两个。

## 跨块解码

每个 8,192 字节的片段都交给流式解码器；不完整的字节序列留到下一个片段：

- **UTF-8**：`TextDecoder("utf-8", { fatal: true })`，加 `{ stream: true }`。一个两到四字节的字符被片段边界切开时，由下一个片段补全。开头的一个字节顺序标记会被去掉，和 `utf-8-sig` 一样。文件结束时序列不完整，就是错误，和 Python 一样。
- **UTF-16**：必须有字节顺序标记，由它选择 `utf-16le` 或 `utf-16be`；然后使用流式的 `TextDecoder`。一个码元或一对代理项被片段边界切开时，由下一个片段补全。文件长度是奇数，或以单独的代理项结尾，在文件结束时报错。
- **GB18030**：字节先切成一、二或四字节的完整序列，再交给浏览器的解码器，因为有 22 个序列在 Python 里的解码结果不同，要按 Python 的结果替换。被片段末尾切断的序列（在第一、第二或第三个字节之后）先留着，和下一个片段接在一起。

这些在 1.0 里并不是新的：读取器原来就按 8,192 字节的片段解码，只是片段来自整块缓冲区。新的地方是片段来自流，而且测试会在每个字节处切开流。

## 跨块的行

`LineReader` 按 `io.TextIOWrapper(newline="")` 的方式给出行：以 `\n`、`\r\n` 或 `\r` 结束，并保留行尾。

- **CRLF 被片段边界切开。** 片段以 `\r` 结尾时，无法知道后面是不是 `\n`。这个 `\r` 会留到下一个片段解码之后，和 Python 的 `IncrementalNewlineDecoder` 一样；到了文件结尾，它自己就是一个行尾。
- **带换行的引号值。** CSV 读取器是一个逐行工作的状态机（状态与 `Modules/_csv.c` 相同）。跨行的引号字段在行与行之间保持状态；从 1.0 起，在片段之间也保持：需要的行还没到时，读取器返回“还需要更多”，保留已经读到的字段、正在读的字段、它的码点长度和状态，等下一个片段到了再接着读。
- 拒绝信息里的**行号**是读过的行数，包括引号值里的行，和 `reader.line_num` 的算法一样（`line-number-after-quoted-break`）。
- 131,072 个码点的**字段上限**跨片段累计（`refused-field-limit`、`field-at-limit`）。

## 摘要值

`crypto.subtle.digest` 需要一次拿到全部输入，所以不能用它计算流的摘要值。读取器因此使用 `sha256.ts` 里的 SHA-256，并把它改成分段接收输入。从 0.4.0 起，打包的核对函数在没有 `crypto.subtle` 的环境里用的就是这个实现；测试用随机输入、每个核对样例的文件，以及按各种大小分段的输入，把它和 `crypto.subtle` 对比。

Python 计算文件每个字节的摘要值，包括最后一行之后剩下的部分。`ByteFeed` 把交出的每个字节都计入摘要值；文件读到结尾，就是每个字节都交出过。被拒绝的文件没有摘要值，和命令行一样。

配置文件很小，仍然整个读入；运行环境有 `crypto.subtle` 时用它计算摘要值。

## 内存里保留什么

| 保留的内容 | 大小 |
| --- | --- |
| 一块读取缓冲区，以及最多一个跨块复制的 8,192 字节片段 | 1 MiB |
| 已解码、还没有切成行的文本 | 一个片段；一行比片段长时是一行 |
| 每个来源行的键和比较字段的值，按列存放 | 只有用到的列 |
| 键索引：每个不同的来源键一项 | |
| 每个来源行：带着它的键的目标行数（8 字节）和它的状态（1 字节） | |
| 目标行的值，只在与来源不同时保留 | 不同的那些行 |
| 两份报告，作为 `Blob`，每次约 1 MiB 地写入 | 不在 JavaScript 堆里 |

目标文件逐行建立索引，不保留任何目标行，和命令行一样。除了行数和用到的列数，上面没有一项会随文件大小增长，而这两者都受下面的上限限制。

为了降低峰值做了两处改动，都不影响结果：比较字段的值按字段各放一个数组，而不是每行一个数组；报告分段写入 `Blob`，而不是先把一百万个字符串收集成一个列表。

## 进度和剩余时间

Worker 大约每秒报告十次：当前阶段、每一侧读到的行数、读到的字节数。页面把这些换算成“工作完成了多少”的一个比例。读取按两个文件的字节计算；评估和写报告各占总量的固定份额，按已完成的记录推进。

剩余时间由完成的比例和已经花掉的时间估算。显示规则见[浏览器说明](1.0-browser.md#progress-while-a-check-runs)（英文）：最初半秒什么也不显示；之后显示一个随时间递减的数值，只有在不得不调高时才调高。

## 上限和拒绝

默认上限不变：每个文件 209,715,200 字节（200 MiB），读取任何字节之前根据 `File.size` 检查；每个文件 1,000,000 个数据行，读到第 1,000,001 行时拒绝。信息也不变：`NAME: file size N bytes exceeds --max-bytes limit of 209715200` 和 `NAME: exceeds --max-rows limit of 1000000`。

读取过程中流出错（文件在选择之后被移动或修改），核对就失败：不显示结果，也不使用任何不完整的内容。

## 怎样证明结果相同

1. **每个核对样例，切成块**（`ui/src/test/offline/streaming.test.ts`）。不超过 4 KiB 的输入，在每个字节处切成两块各运行一次，再按每块一个字节的流运行一次；更大的输入，用固定种子的生成器选 24 个切点运行，再切成 41 块运行。每次运行都必须给出样例里的退出码、摘要、拒绝信息和两份报告：总共超过 20,000 次运行。
2. **生成的文件。** 三种编码的文件，带有引号内的换行、CR LF、空行和两到四字节的字符，在随机位置切成 2、7、300 和 5,000 块读取，得到的行、摘要值和行尾必须与整个读取时相同。损坏的文件（无效字节、被截断的文件、没有闭合的引号、过宽的行）不论在哪里切开，都必须以同样的信息被拒绝。
3. **`ByteFeed`。** 不论送入什么，它交出的片段都恰好是 8,192 字节；流重复使用缓冲区时，它手里的字节不会丢；它的摘要值与 `crypto.subtle` 给出的相同。SHA-256 还按 1 到 200 字节的每一种分段大小测试过。
4. **与 Python 的随机对比。** 原有的随机对比测试（CI 里 300 个样例）现在通过流式读取器运行。
5. **大文件运行。** `FA_LARGE=1 check-large.spec.ts` 把页面对两个 1,000,000 行文件给出的摘要与命令行的摘要对比；页面定时器迟到 100 毫秒，或者 Worker 的内存不受限制时，测试失败。

## 测量

两个 1,000,000 行的文件（各 45 MB），`FA_LARGE=1 npx playwright test e2e/check-large.spec.ts --project chrome`，macOS 27.2 上的 Google Chrome，Apple 芯片，各运行三次。内存通过 Chrome DevTools Protocol（`Runtime.getHeapUsage`）每 50 毫秒读取一次，页面和它的 Worker 分别读取：使用中的 JavaScript 堆，以及 ArrayBuffer 的后备存储（整个读入的文件就放在那里）。

| | 之前（0.7.0，`500ca45`） | 之后（1.0.0） |
| --- | --- | --- |
| 从点击“核对”到出现结果 | 2.29 秒、2.28 秒、2.26 秒 | 2.21 秒、2.39 秒、2.22 秒 |
| 页面 100 毫秒定时器的最长延迟 | 1 毫秒、2 毫秒、2 毫秒 | 1 毫秒、2 毫秒、1 毫秒 |
| Worker 的 JavaScript 堆峰值 | 525 MiB、533 MiB、533 MiB | 178 MiB、174 MiB、174 MiB |
| Worker 的 ArrayBuffer 峰值 | 152 MiB、157 MiB、157 MiB | 57 MiB、58 MiB、57 MiB |
| 页面的 JavaScript 堆峰值 | 10 MiB | 10 MiB |

时间在页面里测量：从点击“核对”到结果出现在文档里。堆的峰值是原来的三分之一，目标是一半。时间与原来相同，差别在各次运行的波动之内：用 TypeScript 计算摘要值花的时间，和以前整个读入文件花的时间相当。

峰值里包括已经不用、但还没有回收的内存，所以它取决于浏览器什么时候回收。ArrayBuffer 里剩下的部分就是这一类：Worker 为每个文件只持有一块 1 MiB 的读取缓冲区。
