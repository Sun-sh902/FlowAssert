# The browser check in 1.0: design note

Status: FlowAssert 1.0.0. Written before the code and kept in step with it. It covers five additions to the CSV check
page and the saved-report pages: the file profile, the warnings before a check, the result explorer, the character
diff and the redesigned HTML report. [The streaming note](1.0-streaming.md) covers how files are read.

## Rules every part follows

1. **Advisory is never authoritative.** A profile, a warning, a highlight and a filter are read from the files or from
   the report. None of them changes a file, a choice, a statement or a report, and none of them is a conclusion. Each is
   labelled as what it is. The check's result is the only conclusion.
2. **One code path for one number.** A row count shown before a check comes from `readCsv`, the function the check
   reads the file with. A stated total is compared with it by `sameCount`, the function the evaluator uses. A test
   compares the profile's counts with the report's for every golden case and scenario.
3. **Nothing leaves the browser.** Everything runs in the page and its two workers. No request is made between choosing
   a file and downloading a report, and the online demo's Content Security Policy still forbids every connection.
4. **Nothing is remembered.** A profile lives as long as the file is chosen. Explorer state in the address holds
   numbers and fixed words only, never a value, a key or a column name from a file.
5. **Every state is designed**, in English and Chinese, light and dark, desktop and phone width, by keyboard alone.

## The file profile

A file is accepted from the "Choose a file" button or by dropping it on its panel. The whole panel is the drop target;
while a file is dragged over it, the panel shows a dashed brand outline and the words "Drop the file here". Dropping
more than one file takes none and says "Drop one file". The button stays the keyboard path.

As soon as a file is chosen, two things happen in the profile worker:

1. **The header** is read from the start of the file, as before, so the column lists fill at once.
2. **The profile** reads the whole file as a stream, with `readCsv` and every column selected. It gives:

| Shown | From |
| --- | --- |
| Data rows | The count `readCsv` returns: blank lines are not rows |
| Columns, each with its number of empty cells | Cells equal to the empty string |
| Encoding | The encoding chosen, never guessed |
| Byte order mark | The file's first bytes: `EF BB BF` for UTF-8; `FF FE` or `FE FF` for UTF-16, which names its byte order; `84 31 95 33` for GB18030, where the mark stays part of the first column name, as Python reads it |
| Line endings | The line endings the reader met: LF, CRLF, CR, or the count of each when they are mixed. A line ending inside a quoted value is counted too, because it is in the file |
| Size | `File.size`, in bytes and in a rounded unit |

The profile is labelled "File profile · read from the file, before any check". The two workers keep apart what is
advisory and what is the check: the profile worker reads headers and profiles, the check worker runs checks, and
cancelling a check never interrupts a profile. A file the check would refuse is refused
here with the same message, because it is the same reader: a malformed row, a byte that does not decode, more rows than
the limit. The existing refusal hint appears under it. A refused file has no profile.

Changing the encoding reads the profile again. A profile that is still being read shows the rows read so far.

The key columns get a second, smaller read, the **key profile**, once a key column is chosen and its file's profile is
ready: the number of rows whose key is empty or only whitespace, and the number of keys that appear in more than one
row. It uses the evaluator's own `key` test and is counted by the same class the check counts source keys with.

## Warnings before the check

Once the facts are known, the premises section shows what the check will do with them, under the heading "Before you
check · read from the files". Each line says what the check will do, never what the person should do, and changes no
choice.

| Fact | Line |
| --- | --- |
| A stated total differs from the profile's rows, and the completeness statement is ticked | "If you check now, the destination statement will not be applied: the export has 4 rows, not 5." (for the source: "the source statement … the file has …") |
| The same, with the statement not ticked | "If you check now, the destination total will be recorded as not matching: the export has 4 rows, not 5." |
| Source key column has rows without a key | "If you check now, the batch cannot be Verified: 2 source rows have no key in this column: `external_id`" |
| Source key column repeats a key | "If you check now, the batch cannot be Verified: 3 keys appear in more than one source row in this column: `external_id`" |
| Destination key column has rows without a key | "If you check now, absence and uniqueness will stay unknown: 1 destination row has no key in this column: `external_id`" |
| Destination key column repeats a key | "If you check now, no source record with one of these keys can be Verified: 2 keys appear in more than one destination row in this column: `external_id`" |
| A chosen column is not in its file | "If you check now, it will be refused, because this column is not in the destination export: `hs_email`" |

A column name always comes last, after a colon, as a value of its own: it is shown exactly as the file writes it and
is never translated, and the sentence before it reads the same in English and in Chinese.

Each line is exact about the evaluator. A source total that differs makes the source population unknown whether or not
the statement is ticked; a destination total that differs withdraws destination coverage only when the destination
statement is ticked, and otherwise is only recorded. A source record whose key appears in more than one destination row
has a failed uniqueness rule, or, when its own key is repeated, no rule result at all: in neither case is it Verified.

A warning is shown only while it is true of the current choices. When nothing is known yet, or nothing contradicts,
the block is absent; it never says "no problems", because the profile is not a check.

The notes that 0.7.0 shows after a check, beside a stated total that the last check did not apply, stay as they are.
They are read from that check's report; these lines are read from the files.

## Progress while a check runs

The progress area shows the phase (reading the source, reading the destination, evaluating the records, writing the
reports), the rows read on each side, a bar, and an estimate of the time left.

The estimate is honest about what it is: "about 4 s left", from the bytes read so far and the time they took. It is
not shown for the first half second or before 2% of the work is done ("estimating the time left…"). The shown value
counts down with the clock and is corrected upwards only when the new estimate exceeds it by more than a quarter and
by more than one second, so it never jumps backwards by more than it has to. Cancel ends the worker at once.

## The result explorer

The result, a saved report and each side of a comparison use one explorer. It reads records through one interface with
two implementations: the check worker, which still holds the evaluation and builds each record as it is asked for, and
a saved report's records in memory. The page asks for a window of rows at a time, so a result of 1,000,000 records is
never copied into the page.

**Filters.** State (Verified, Mismatch, Unverified); rule (`existence`, `uniqueness`, or one compared field) with a
status (pass, fail, unknown); "destination-only" switches the list to the destination-only records of a scope `exact`
report. **Search** matches keys that contain the text typed, exactly as written, case included. **Sort** is by row,
ascending or descending. The line above the list says how many records match, of how many.

**The list** is virtualised: fixed-height rows, and only the visible ones are in the document. It is a listbox with
one tab stop: arrow keys, Page Up, Page Down, Home and End move through it, and each option carries its position and
the size of the set. Above about 250,000 rows the scroll bar is scaled, so the list's height stays within what
browsers can lay out.

**The panel.** Selecting a record opens it beside the list (below it on a phone): its row, key, state, the number of
destination rows carrying the key, and every rule result with its reason and both values.

- A report written with `--details problems`, which is the default, holds no rule results for a Verified record. The
  panel says so: "This report was written with details: problems. It records that this record is Verified, but not its
  rule results or values." A rule filter then says how many Verified records it cannot test.
- A report written with `--redact-values` has no keys and no values. Search is turned off, and says why.

**The address.** The explorer's state is in the address hash, so a view can be linked: `state`, `rule` as the position
of the rule (`e` existence, `u` uniqueness, `f1` the first field…) with its status, `only` for destination-only, `sort`
and `row` for the selected record. Search text is never written to the address, because it is a piece of a key. On the
CSV check page a result does not survive a reload, so the address there restores nothing.

## The character diff

For a field result that failed, the panel shows where the two values differ.

- The two values are aligned by code point: a common prefix and suffix, and between them a longest common subsequence
  with fixed tie-breaking. When the two middles are longer than 65,536 cells of alignment table, they are shown as
  replaced, and the panel says the values were too long to align.
- Deleted characters are marked on the source value, inserted ones on the destination value. Marks differ in form as
  well as colour: a deletion is struck through, an insertion underlined.
- Invisible characters in a highlighted part, and at the start and end of a value, are drawn as visible tokens: a
  space as `·`, a non-breaking space as `NBSP`, a tab as `→`, a line feed as `↵`, a carriage return as `␍`, and
  zero-width and other format characters by their names (`ZWSP`, `ZWNJ`, `ZWJ`, `BOM`, `WJ`, `SHY`). Any other
  character that differs and is not ASCII has its code point listed under the values (`é U+00E9` against
  `e U+0065 + U+0301`), which is what makes a difference of Unicode normalisation or a look-alike letter visible.
- In the browser, two notes are added when they are true: that the values are equal after Unicode normalisation (NFC,
  or NFKC), and that they differ only in upper and lower case.
- For a rule that ignores part of the value (`trim`, `casefold`, `digits`, `date:FORMAT`), the panel shows the values
  as written and the values as compared, both as the report records them, and highlights the compared ones, because
  those are what the rule found different.

It is labelled: "This highlights where the two values differ. The rule's result above is the conclusion." The same
alignment, written the same way in Python and TypeScript, draws the highlights of the HTML report.

## The HTML report

The standalone HTML report is redesigned in the same language as the app, and both implementations write the same
bytes.

1. **Verdict.** The seal with the batch result, the claim or "No claim is made: the result is not Verified.", the rows
   read and the three counts, when it was evaluated and by which evaluator.
2. **Premises.** Each premise with what was stated, its origin, the rows read and whether a stated total matched; then,
   in words, whether it was applied: "applied", "not applied: the stated total differs from the rows read", "not
   stated". The sentence that FlowAssert does not verify them.
3. **Records that are not Verified.** Each as a card: row, key, state, and every rule result with its reason; for a
   failed field the two values with the character highlighting, and the compared values for a rule that normalises.
4. **Destination-only records**, for scope `exact`.
5. **Where the source was read**, for a report from a connector.
6. **Limitations**, with the four members that are never assessed.
7. **Inputs**: digests, encodings, the obligation.

Its constraints are unchanged: no script, no external resource, a Content Security Policy that blocks everything but
its own inline style, every value escaped. It follows `prefers-color-scheme`, and prints on A4 and Letter with a
record card never split across pages when it fits on one. At phone width nothing scrolls sideways: records are cards,
not a wide table.

The fonts are the reader's own: the page names system serif, sans-serif and monospace stacks and embeds nothing.
