## What changes, and what must not

Up to 0.7.0 the worker read each file whole (`File.arrayBuffer()`), parsed it, and hashed the same buffer with
`crypto.subtle`. Both files were therefore in memory at once, beside everything the check keeps.

From 1.0 the worker reads each file through `File.stream()` and keeps no more of it than the chunk in hand.

What must not change is anything a person or a program can see: the records, every refusal with its line number, the
digests, and both reports byte for byte. The command-line checker is the reference. It reads with
`io.TextIOWrapper(newline="")`, which decodes the file 8,192 bytes at a time, only when the CSV reader needs another
line. Which problem is met first, a malformed row or a byte that does not decode, depends on that order, and two
golden cases hold it (`chunk-csv-error-before-later-decode-error`, `chunk-decode-error-in-first-chunk`).

## From a file to 8,192-byte chunks

A stream gives chunks of whatever size the browser chooses. The reader does not depend on them:

1. **`ByteFeed`** takes the stream's chunks and hands out pieces of exactly 8,192 bytes, the last one shorter. A piece
   that lies inside one stream chunk is a view of it; a piece that straddles two is copied once. Every byte handed out
   also goes to the digest, in file order.
2. **`LineReader`** asks for the next piece only when it holds no whole line, exactly when Python's text layer reads
   again.
3. Taking a piece is synchronous while the feed has 8,192 bytes buffered. The reader waits (`await`) only when the feed
   is empty and the stream has more. So the decoder sees the same bytes, in the same pieces, at the same moments as
   before, whatever the stream's chunk sizes are, and the wait happens a few hundred times per file, not once per row.

The packaged checker (`checkCsv`) takes its files as bytes already in memory. It reads them through the same feed, as a
stream of one chunk, so there is one reader and not two.

## Decoding across chunks

Each 8,192-byte piece is decoded by a streaming decoder that keeps an incomplete sequence for the next piece:

- **UTF-8**: `TextDecoder("utf-8", { fatal: true })` with `{ stream: true }`. A character of two, three or four bytes
  split between pieces is completed by the next piece. One leading byte order mark is removed, as `utf-8-sig` does. At
  the end of the file, an incomplete sequence is an error, as in Python.
- **UTF-16**: the byte order mark is required and chooses `utf-16le` or `utf-16be`; then a streaming `TextDecoder`. A
  code unit, or a surrogate pair, split between pieces is completed by the next. A file of odd length, or one that ends
  on a lone surrogate, is an error at the end.
- **GB18030**: the bytes are split into whole sequences of one, two or four bytes before they reach the browser's
  decoder, because 22 sequences decode differently in Python and are replaced as Python decodes them. A sequence cut
  by the end of a piece (after its first, second or third byte) is held back and joined with the next piece.

None of this is new in 1.0: the reader already decoded in 8,192-byte pieces from a whole buffer. What is new is that
the pieces come from a stream, and that the tests now cut the stream at every byte.

## Lines and rows across chunks

`LineReader` yields lines as `io.TextIOWrapper(newline="")` does: ending at `\n`, `\r\n` or `\r`, with the ending
kept.

- **CRLF split between pieces.** A piece that ends with `\r` cannot say whether a `\n` follows. The `\r` is held back
  until the next piece is decoded, as Python's `IncrementalNewlineDecoder` holds it; at the end of the file it is a
  line ending by itself.
- **A quoted value with line breaks.** The CSV reader is a state machine over lines (the states of `Modules/_csv.c`).
  A quoted field that spans lines keeps its state between lines, and from 1.0 between pieces too: when the reader
  needs a line that has not arrived, it returns "need more", keeping the fields read so far, the field in progress,
  its length in code points and its state, and continues from there when the next piece is in.
- **The line number** of a refusal is the count of lines read, including the lines inside quoted values, as
  `reader.line_num` counts them (`line-number-after-quoted-break`).
- **The field limit** of 131,072 code points is counted across pieces (`refused-field-limit`, `field-at-limit`).

## The digest

`crypto.subtle.digest` takes the whole input at once, so a stream cannot be hashed with it. The reader therefore uses
the SHA-256 of `sha256.ts`, changed to take its input in pieces. It is the implementation the packaged checker has
used since 0.4.0 where `crypto.subtle` is missing; the tests compare it with `crypto.subtle` on random inputs, on every
golden file, and on inputs fed in pieces of every size.

Python hashes every byte of the file, including what is left after the last row. The feed hashes every byte it hands
out, and a file that is read to its end has handed out every byte. A refused file has no digest, as on the command
line.

The configuration file is small and is still read whole and hashed with `crypto.subtle` where the host has it.

## What is kept in memory

| Kept | Size |
| --- | --- |
| The stream chunk in hand, and at most one 8,192-byte piece copied across a chunk boundary | The browser's chunk size |
| Decoded text not yet split into lines | One piece, or one row when a row is longer |
| For each source row: its key and the values of the compared fields, column by column | The columns used only |
| The key index: one entry per distinct source key | |
| For each source row: the count of destination rows with its key (8 bytes) and its state (1 byte) | |
| A destination row's values, only where they differ from the source's | The rows that differ |
| The reports, as `Blob`s built from pieces of about 1 MiB | Outside the JavaScript heap |

The destination is indexed row by row and no destination row is kept, as on the command line. Nothing above grows with
the size of the files beyond the rows and the columns used, and both are bounded by the limits below.

Two things were changed to bring the peak down, neither of which changes a result: the compared values are kept in one
array per field instead of one array per row, and the reports are written into `Blob`s in pieces instead of being
collected as one list of a million strings first.

## Progress and the time left

The worker reports, about ten times a second: the phase, the rows read on each side, and the bytes read. The page
turns that into one fraction of the work done. Reading counts as the bytes of both files; evaluating and writing are
each counted as a fixed share of the total, advanced by the records done.

The time left is estimated from the fraction done and the time it took. The rule for showing it is in
[the browser note](1.0-browser.md#progress-while-a-check-runs): nothing for the first half second, then a value that
counts down and is raised only when it must be.

## Limits and refusals

The default limits stay: 209,715,200 bytes per file (200 MiB), checked from `File.size` before a byte is read, and
1,000,000 data rows per file, refused at row 1,000,001 while reading. The messages are unchanged:
`NAME: file size N bytes exceeds --max-bytes limit of 209715200` and `NAME: exceeds --max-rows limit of 1000000`.

A stream that fails while it is read (the file was moved or changed after it was chosen) fails the check: no result is
shown and nothing partial is used.

## How the result is proved the same

1. **Golden cases.** Every golden case the page can run is run through the streaming reader and must give the golden
   reports, summary and exit status.
2. **Every byte offset.** For every golden input file of at most 4 KiB, the file is fed as two chunks split at every
   byte offset, and as a stream of one-byte chunks; each run must give the same rows, the same digest and the same
   refusal as the file fed whole.
3. **Random offsets.** Larger golden files, and generated files of mixed encodings, quoting and line endings, are fed
   in chunks cut at random offsets from a seeded generator; the seed is printed on failure.
4. **Random parity with Python.** The existing random parity test runs through the streaming reader.
5. **The large-file run.** `FA_LARGE=1 check-large.spec.ts` compares the page's summary of two files of 1,000,000
   rows with the command line's.

## Measurements

Two files of 1,000,000 rows (45 MB each), `FA_LARGE=1 npx playwright test e2e/check-large.spec.ts --project chrome`,
Google Chrome on macOS 27.2, Apple silicon, three runs each. Memory is read through the Chrome DevTools Protocol
(`Runtime.getHeapUsage`) every 50 ms, for the page and for its worker: the JavaScript heap in use, and the backing
stores of array buffers, which is where a file read whole is held.

| --- | --- | --- |
| Time from Check to the result | 2.31 s, 2.32 s, 2.32 s | to be measured |
| Longest delay of a 100 ms page timer | 1 ms | to be measured |
| Peak worker JavaScript heap | 525 MiB, 534 MiB, 540 MiB | to be measured |
| Peak worker array buffers | 152 MiB, 157 MiB, 155 MiB | to be measured |
| Peak page JavaScript heap | 10 MiB | to be measured |
