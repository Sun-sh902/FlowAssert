# FlowAssert for iPhone and iPad: design note

Status: work towards FlowAssert 1.2.0, not released. Written before the code and kept in step with it.

The app runs the same check as the command line, on files and on the two read-only connectors, on an iPhone or an
iPad. It is a native SwiftUI app for iOS 17 or later. It has no checker of its own: the verdict, every rule result,
count, refusal text and byte of a report come from the packaged checker, `ui/dist-lib/flowassert-check.js`, running in
WebKit inside the app.

## Engine

**Decision.** The app has no checker of its own. The verdict, every rule result, count and refusal text, and every
byte of a report come from the packaged checker, `ui/dist-lib/flowassert-check.js`, built by `npm run build:lib`,
running in WebKit inside the app. A third implementation in Swift would be a third place for two implementations that
already have to agree byte for byte to differ.

### The host

- A `WKWebView` that is never shown (`ios/FlowAssert/Engine/CheckerEngine.swift`) loads one page,
  `flowassert://engine/engine.html`, through a `WKURLSchemeHandler` (`EngineSchemeHandler.swift`). No file URL is
  loaded and no website data is kept (`WKWebsiteDataStore.nonPersistent()`).
- The page loads two scripts from the same scheme: the packaged checker, copied unchanged into the app by
  `node ios/scripts/checker.mjs` (`--check` fails when the copy is not the build, as the n8n example's check does), and
  `host.js`, which only carries things between Swift and `FlowAssert.checkCsv` and changes no byte of a result.
- Its Content Security Policy, in the page and in every response, is `default-src 'none'; script-src
  flowassert://engine; connect-src flowassert://engine`. A content rule list blocks every load that is not of
  `flowassert://engine/` or of the page's own Blobs (`blob:flowassert://engine/…`), and the page may not navigate.
  `EngineHostTests` shows that a connection, an image and a script from anywhere else are refused before they are sent.
- A file's bytes go to the page through the scheme handler (`flowassert://engine/input/TOKEN`, a token that lives for
  one check), never as text in a script. The result comes back as the object `checkCsv` returns.
- WebKit, not bare JavaScriptCore: the checker needs `TextDecoder` with fatal utf-8, utf-16 and gb18030, and Blob,
  `ReadableStream` and `DecompressionStream("deflate-raw")` for a workbook; JavaScriptCore alone has none of them.
  Before any check the app asks `FlowAssert.hostProblem(["utf-8", "utf-16", "gb18030"])`, now part of the packaged
  checker's global. In iOS 27.2 on the simulator it is `null`; if it ever is not, the app shows the checker's words and
  does not check. The page is a secure context, so the checker hashes the configuration with `crypto.subtle`.
- Every premise's `origin` is `iPhone and iPad app`, a new value that [Compatibility in 1.x](../compatibility.md)
  allows as an addition. Nothing else in a report changes.

One finding on the way, in the host and not in WebKit: the first content rule list allowed only `flowassert:` loads,
and WebKit reads a Blob by loading its `blob:` URL, so every workbook failed with `NotReadableError` (exit status 4).
Allowing the page's own `blob:flowassert://engine/` URLs fixed it; no other change was made.

### Parity

`ios/FlowAssertTests/EngineParityTests.swift` runs, through `CheckerEngine` exactly as the app runs a check, the cases
`node ios/scripts/engine-cases.mjs` writes, and compares the exit status, the summary, the message and both reports, as
bytes, with two references: the command line (`offline/verify.py`, with the arguments the CSV check page is equivalent
to, or the golden files themselves) and the same bundle in Node (a `node:vm` context with only the globals it needs).
Only `evaluated_at` is left out. A conformance case is also held to its `expected` member.

| Cases | Number | References | Differences in WebKit |
| --- | --- | --- | --- |
| Every golden case the CSV check page can run (`offline/golden/`, marked `page`), with every encoding case among them: utf-8 with and without a byte order mark, utf-16 LE and BE, gb18030 and its Python mapping, and each decode refusal | 59 | The golden files, Node | 0 |
| Every case of `offline/golden-xlsx/` | 71 | The command line, Node; 3 (an unknown format, an encoding with a workbook, a worksheet without the format) are option combinations each implementation refuses in its own words and the app never sends: Node only | 0 |
| Every conformance case, its rows written as CSV files | 38 | The command line, Node, `expected` | 0 |
| The hostile workbooks of the .xlsx parity test (`ui/src/test/offline/hostile-workbooks.ts`) | 31 | The command line, Node | 0 |
| Two CSV files of 1,000,000 rows; a workbook of 3.0 MB (192,000 rows) and one of 49.9 MB (500,000 rows, 4 columns), each against the 1,000,000-row destination | 3 | The command line, Node | 0 |

Before the WebKit run, the two references were compared with each other on every case both can express: no
difference.

### Time and memory

On the iPhone 18 Pro simulator (iOS 27.2) on the build machine, two runs each (`ios/scripts/measure-engine.sh`, one
`xcodebuild` run per case, sampling `ps` every 0.1 s). Time is from asking the engine to the result in Swift; the
check alone (`checkCsv`, by the page's clock) is within 0.1 s of it. Memory is the peak resident size of each process
on the Mac, which is what a simulator process is: it compares runs, and is not an iPhone's memory footprint. The app
process includes the test, which holds both references' reports for the comparison.

| Case | Time | Node 26, same bundle | WebContent peak | Networking peak | App peak |
| --- | --- | --- | --- | --- | --- |
| Two CSV files of 1,000,000 rows (44 MB each) | 6.96 s, 7.00 s | 3.26 s, 3.22 s | 1,582 MiB, 1,566 MiB | 114 MiB | 802 MiB |
| Workbook of 3.0 MB against 1,000,000 CSV rows | 1.96 s, 2.04 s | 1.69 s, 1.67 s | 835 MiB, 837 MiB | 122 MiB | 398 MiB |
| Workbook of 49.9 MB against 1,000,000 CSV rows | 4.49 s, 4.55 s | 4.29 s, 4.28 s | 1,617 MiB, 1,741 MiB | 167 MiB | 582 MiB |

What this shows, and what it does not:

- Moving the bytes in and the reports out costs about 60 ms; the time is the check. JavaScriptCore reads CSV at about
  half Node's speed, and workbooks at about the same.
- The JSON report of the 1,000,000-row check is 95 MB of text; it is built in the page and crosses to Swift as one
  string. The page's peak of about 1.6 GB is the inputs, the check's own memory and the reports at once. Whether an
  iPhone keeps a WebContent process of that size is not known from a simulator; it is measured on the owner's iPhone
  in step 5, and the performance pass of step 5 works on it.
- The simulator runs on the Mac's processor and memory, so these times are not an iPhone's.

## Screens

What the app must show, before how it looks. Every screen follows the rules of the browser check
([1.0 design note](1.0-browser.md#rules-every-part-follows)): what is read from a file is labelled as read, not as a
conclusion; the check's result is the only conclusion; nothing is remembered that the person did not ask to keep. Words
from the checker (a verdict, its summary line, a refusal, a reason) are shown exactly as the checker wrote them.

### The check (one screen, four parts)

1. **Source.** One of: a file (CSV or `.xlsx`), chosen from Files, dropped (iPad), or opened from another app (Files'
   share sheet, "Open in FlowAssert"); or a Google Sheets range (spreadsheet ID and range). For a file: its name, size,
   format; for a CSV file its encoding (`utf-8`, `utf-16`, `gb18030`), never guessed; for a workbook with several
   sheets, the worksheet, chosen among the checker's own listing (`listSheets`), with nothing read until one is chosen.
   For a sheet: what the read shows and what it does not, in the connector note's words, shortened.
2. **Destination.** One of: a file, as above; or HubSpot contacts, with the same note.
3. **Match.** The key column in each input and one or more compared fields, each a source column, a destination column
   and a rule (`exact`, `trim`, `casefold`, `digits`, `date:FORMAT` with its format typed), and the scope (`source` or
   `exact`). Columns are read from the inputs' headers; for a connector they are typed (a HubSpot property, a sheet's
   header). Or an imported configuration file, read as bytes so that its SHA-256 is the file's, and shown as what it
   holds; a configuration can be exported.
4. **What you state** ("not checked by FlowAssert"): the two completeness statements, the two totals and "Allow
   identical content", with the browser page's titles and explanations word for word, and the sentence that a wrong
   statement gives a wrong result. Then the options the command line has and the page does not: details (`problems`,
   `all`), redact values, the two limits, each at its default until changed.

**Check** runs when both inputs and the key and one field are chosen; until then it says what is missing. While it
runs: what is being read, the rows read on each side, and Cancel. A refusal shows the checker's message, unchanged,
with nothing else concluded.

### The result

- **The verdict**: the state word, large, its shape, and the checker's summary line (`Mismatch: 4 rows of 4`), the three
  counts, and the claim or "No claim is made: the result is not Verified." VoiceOver reads the verdict first.
- **The summary**: the checker's printed summary, as text, for the person who reads it as the command line prints it.
- **Records**: every record, filtered by state (opening on those not Verified), searchable by key, with its row, key and
  state; a list of 1,000,000 records scrolls without loading them all.
- **A record**: its rules, each with status and reason; for a field, the source and destination values side by side,
  and the compared forms for a rule that normalises; where they differ, which characters (the character diff of the
  browser, from the same report).
- **Records to resend**: the checker's export files, each with its rows and meaning, to share or save.
- **Export**: the JSON and HTML reports, byte for byte as the checker wrote them, through the share sheet and to Files.
- **Keep this report**: saves the report on this device; nothing is kept unless asked.

### Saved reports

Reports kept on this device, newest first, and reports imported from Files (written by the command line, the browser,
the Action or n8n), each opened through the checker's own saved-report reader, so a report that is not a valid
FlowAssert report is refused and nothing is kept. Delete one, or all with a confirmation. An imported report is not
authenticated, and the screen says so.

### Credentials

Google Sheets (an API key, for a sheet shared for viewing, or an OAuth access token) and HubSpot (a private app access
token). Each is typed once, kept in the Keychain on this device only, and never shown again: the screen says "Saved"
and offers Remove. What each is for and which scope to grant, in the connector notes' words.

### The empty state

The first screen with nothing chosen: the check's four parts, empty, each saying what it takes. No sample data is
loaded unless the person asks for an example.

### iPhone and iPad

- **iPad**: a sidebar (Check, Saved reports, Credentials) and the check beside the result, or the result alone; files
  dropped from Files onto an input. Every orientation.
- **iPhone**: one column; the result is pushed over the check. A file opened from Files or another app's share sheet
  ("Open in FlowAssert") asks whether it is the source or the destination.

### Directions

Five directions for the check screen and the result screen were shown to the owner as static mockups (simulator
screenshots of throwaway SwiftUI views, iPhone and iPad, light and dark, with the synthetic example data), each with a
one-line idea. All five share the rules above: no logo row, colour only for the verdict, each verdict with its own
shape as well as its word (a filled circle with a check for Verified, a filled diamond with a cross for Mismatch, a
dashed circle with a question mark for Unverified, a prohibition sign for refused, a triangle for failed), and system
glass only on the floating Check button.

| | Direction | Idea |
| --- | --- | --- |
| A | Grouped form | One scrolling grouped form, as the system's settings; the result pushed over it, grouped by state |
| B | Mapping | Two input cards and a table of the lines between them (source column, rule, destination column); the result counts each rule on the same table |
| C | Steps | One decision per screen, the completeness statements asked on their own; the result read like the report |
| D | Sentence | The check written as one sentence of tappable parts; the result in sentences and cards with both values side by side |
| E | Workspace | iPad first: a sidebar, the inputs beside a table of records with a column per rule |

**The owner chose A, Grouped form** (14 November 2026), with no change asked for. The app is built in that direction:
one grouped form on the check screen, the result pushed over it on iPhone, and on iPad a sidebar beside the same form
and result.

## Files: the check as built

Built in direction A for files: CSV and `.xlsx`, on iPhone and iPad.

### What runs where

| Part | Where | From |
| --- | --- | --- |
| The check: verdict, records, counts, refusals, summary, both reports, the records to resend | WebKit | `checkCsv` of `flowassert-check.js` |
| The file profile shown before a check, and a file's refusal | WebKit | `profileCsv` and `profileXlsx` (`profile.ts`), the browser's, through `flowassert-app.js` |
| A workbook's sheets, before any is read | WebKit | `listSheets` (`xlsx.ts`) |
| The configuration file the person's choices make, for export | WebKit | `canonicalConfig` (`check.ts`), the page's writer |
| The result screen: the verdict, the claim, the counts, the premises, "What this result means", the records, a record's rules | WebKit | The JSON report the check wrote, opened with the saved-report reader (`savedReport.ts`), listed by the explorer (`explore.ts`), explained by `explain.ts` |
| Where two values differ | WebKit | `align`, `pieces`, `codePoints`, `notes` (`chardiff.ts`) |
| Choosing files, the form, sharing and saving files, keeping reports | Swift | |

`flowassert-app.js` (`npm run build:app`, `ui/src/offline/appLib.ts`) is a second script built from the same sources,
so that the packaged checker, which n8n users paste into a code step, does not grow. It checks nothing.
`ui/src/test/offline/app-bundle.test.ts` runs it as the app's page has it, with every golden report: each is opened as
the report it is, and its records are listed in its order. `ios/scripts/checker.mjs --check` holds both copies in the
app to their builds.

Swift decides only how a file is read, never what it holds: a file is a workbook when its name ends in `.xlsx`, `.xlsm`,
`.xlsb`, `.xltx` or `.xls` or its first bytes are a ZIP archive's or an OLE compound file's, as the CSV check page
decides, so that a legacy or protected workbook gets the workbook refusal and not a CSV one.

### The check screen

- **Source** and **Destination**: Choose a file (Files), drop one (iPad), or open one from another app; then the
  encoding of a CSV file (never guessed), the worksheet of a workbook with several sheets (hidden ones marked, nothing
  read until one is chosen), and the profile, labelled "read from the file, before any check", or the refusal a check
  would give the file in the checker's words.
- **Key**, **Compared fields** (a rule each, with the page's words for each rule, and a date format for `date`) and the
  **scope**. A configuration file can be imported, and is then read by the check as its bytes, so its SHA-256 is the
  file's, while its choices are not changed; it can be exported as the page writes it.
- **What you state**: the page's titles and explanations word for word; the totals are passed as typed, so the checker
  refuses one that is not a count, in its own words.
- **Options**: details, redaction and the two limits, at the command line's defaults until changed.
- **Check** floats over the form (system glass on iOS 26 and later). While a check runs it says so, with Cancel, which
  closes the page.

### The result screen

The verdict first, read by VoiceOver as one sentence that starts with the state ("Mismatch. Mismatch: 4 rows of 4.
Verified 1 · Mismatch 3 · Unverified 0. No claim is made: the result is not Verified."); then the records, "What this
result means", the records to resend, the reports (share sheet and Save to Files, as the checker's bytes, under the
browser's names `flowassert-report.json` and `flowassert-report.html`), Keep this report, the printed summary, what was
stated and the limitations. A refused or failed check shows only the checker's message, and says that nothing is
concluded. The records list asks the explorer for 100 records at a time, so the list of a million records is never
copied out of the page. A record shows every rule result with its reason and the two values side by side; where a rule
failed, the deleted characters are struck through and the inserted ones underlined, and invisible characters are drawn
as the browser's tokens.

A check ending gives one haptic, the same for every result, so that the haptic does not stand in for the verdict.

### Saved reports

Kept only when the person asks: the JSON report's bytes, unchanged, in Application Support, written with complete file
protection, beside a list of what the reader read when the report was kept. A report is reopened, and a report is
imported (from the Saved reports screen, or opened from another app), only through the saved-report reader, so a file
that is not a valid FlowAssert report is refused with its message and nothing is kept. An imported report says that it
is not authenticated. Delete one, or all after a confirmation.
