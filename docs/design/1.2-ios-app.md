# FlowAssert for iPhone and iPad: design note

Status: work towards FlowAssert 1.2.0, not released. Written before the code and kept in step with it.

The app runs the same check as the command line, on files and on the two read-only connectors, on an iPhone or an
iPad. It is a native SwiftUI app for iOS 17 or later. It has no checker of its own: the verdict, every rule result,
count, refusal text and byte of a report come from the packaged checker, `ui/dist-lib/flowassert-check.js`, running in
WebKit inside the app.

## Engine

**Decision.** The app has no checker of its own. The verdict, every rule result, count and refusal text, and every
byte of a report come from the packaged checker, `ui/dist-lib/flowassert-check.js`, built by `npm run build:lib`,
running in WebKit inside the app. A third implementation in Swift would be a third place for two implementations that
already have to agree byte for byte to differ.

### The host

- A `WKWebView` that is never shown (`ios/FlowAssert/Engine/CheckerEngine.swift`) loads one page,
  `flowassert://engine/engine.html`, through a `WKURLSchemeHandler` (`EngineSchemeHandler.swift`). No file URL is
  loaded and no website data is kept (`WKWebsiteDataStore.nonPersistent()`).
- The page loads two scripts from the same scheme: the packaged checker, copied unchanged into the app by
  `node ios/scripts/checker.mjs` (`--check` fails when the copy is not the build, as the n8n example's check does), and
  `host.js`, which only carries things between Swift and `FlowAssert.checkCsv` and changes no byte of a result.
- Its Content Security Policy, in the page and in every response, is `default-src 'none'; script-src
  flowassert://engine; connect-src flowassert://engine`. A content rule list blocks every load that is not of
  `flowassert://engine/` or of the page's own Blobs (`blob:flowassert://engine/…`), and the page may not navigate.
  `EngineHostTests` shows that a connection, an image and a script from anywhere else are refused before they are sent.
- A file's bytes go to the page through the scheme handler (`flowassert://engine/input/TOKEN`, a token that lives for
  one check), never as text in a script. The result comes back as the object `checkCsv` returns.
- WebKit, not bare JavaScriptCore: the checker needs `TextDecoder` with fatal utf-8, utf-16 and gb18030, and Blob,
  `ReadableStream` and `DecompressionStream("deflate-raw")` for a workbook; JavaScriptCore alone has none of them.
  Before any check the app asks `FlowAssert.hostProblem(["utf-8", "utf-16", "gb18030"])`, now part of the packaged
  checker's global. In iOS 27.2 on the simulator it is `null`; if it ever is not, the app shows the checker's words and
  does not check. The page is a secure context, so the checker hashes the configuration with `crypto.subtle`.
- Every premise's `origin` is `iPhone and iPad app`, a new value that [Compatibility in 1.x](../compatibility.md)
  allows as an addition. Nothing else in a report changes.

One finding on the way, in the host and not in WebKit: the first content rule list allowed only `flowassert:` loads,
and WebKit reads a Blob by loading its `blob:` URL, so every workbook failed with `NotReadableError` (exit status 4).
Allowing the page's own `blob:flowassert://engine/` URLs fixed it; no other change was made.

### Parity

`ios/FlowAssertTests/EngineParityTests.swift` runs, through `CheckerEngine` exactly as the app runs a check, the cases
`node ios/scripts/engine-cases.mjs` writes, and compares the exit status, the summary, the message and both reports, as
bytes, with two references: the command line (`offline/verify.py`, with the arguments the CSV check page is equivalent
to, or the golden files themselves) and the same bundle in Node (a `node:vm` context with only the globals it needs).
Only `evaluated_at` is left out. A conformance case is also held to its `expected` member.

| Cases | Number | References | Differences in WebKit |
| --- | --- | --- | --- |
| Every golden case the CSV check page can run (`offline/golden/`, marked `page`), with every encoding case among them: utf-8 with and without a byte order mark, utf-16 LE and BE, gb18030 and its Python mapping, and each decode refusal | 59 | The golden files, Node | 0 |
| Every case of `offline/golden-xlsx/` | 71 | The command line, Node; 3 (an unknown format, an encoding with a workbook, a worksheet without the format) are option combinations each implementation refuses in its own words and the app never sends: Node only | 0 |
| Every conformance case, its rows written as CSV files | 38 | The command line, Node, `expected` | 0 |
| The hostile workbooks of the .xlsx parity test (`ui/src/test/offline/hostile-workbooks.ts`) | 31 | The command line, Node | 0 |
| Two CSV files of 1,000,000 rows; a workbook of 3.0 MB (192,000 rows) and one of 49.9 MB (500,000 rows, 4 columns), each against the 1,000,000-row destination | 3 | The command line, Node | 0 |

Before the WebKit run, the two references were compared with each other on every case both can express: no
difference.

### Time and memory

On the iPhone 18 Pro simulator (iOS 27.2) on the build machine, two runs each (`ios/scripts/measure-engine.sh`, one
`xcodebuild` run per case, sampling `ps` every 0.1 s). Time is from asking the engine to the result in Swift; the
check alone (`checkCsv`, by the page's clock) is within 0.1 s of it. Memory is the peak resident size of each process
on the Mac, which is what a simulator process is: it compares runs, and is not an iPhone's memory footprint. The app
process includes the test, which holds both references' reports for the comparison.

| Case | Time | Node 26, same bundle | WebContent peak | Networking peak | App peak |
| --- | --- | --- | --- | --- | --- |
| Two CSV files of 1,000,000 rows (44 MB each) | 6.96 s, 7.00 s | 3.26 s, 3.22 s | 1,582 MiB, 1,566 MiB | 114 MiB | 802 MiB |
| Workbook of 3.0 MB against 1,000,000 CSV rows | 1.96 s, 2.04 s | 1.69 s, 1.67 s | 835 MiB, 837 MiB | 122 MiB | 398 MiB |
| Workbook of 49.9 MB against 1,000,000 CSV rows | 4.49 s, 4.55 s | 4.29 s, 4.28 s | 1,617 MiB, 1,741 MiB | 167 MiB | 582 MiB |

What this shows, and what it does not:

- Moving the bytes in and the reports out costs about 60 ms; the time is the check. JavaScriptCore reads CSV at about
  half Node's speed, and workbooks at about the same.
- The JSON report of the 1,000,000-row check is 95 MB of text; it is built in the page and crosses to Swift as one
  string. The page's peak of about 1.6 GB is the inputs, the check's own memory and the reports at once. Whether an
  iPhone keeps a WebContent process of that size is not known from a simulator; it is measured on the owner's iPhone
  in step 5, and the performance pass of step 5 works on it.
- The simulator runs on the Mac's processor and memory, so these times are not an iPhone's.
