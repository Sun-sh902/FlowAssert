## 2. 定位:FlowAssert 和普通比对工具的区别

普通比对工具回答“两份数据哪里不同”。FlowAssert 回答“这个结果有没有足够的证据”。后续每个功能都必须服务于这一点:

1. **区分不一致和证据不足。** 找不到记录,不等于记录缺失。
2. **前提必须明说。** 来源是否完整、导出是否完整,都写进报告。
3. **重复不挑。** 一个键对应多条记录时,不会随便选一条比较。
4. **批次和记录分开。** 每条都通过,批次也可能是未验证。
5. **报告可留存。** 带文件摘要、时间和所用规则,事后能复查。

如果某个功能会削弱这些原则,就不做。

## 3. 已知问题和处理方案

2026-11-02 根据代码审查和实测确认。

### 问题 1:内容完全相同的两份文件会被拒绝

`cli.py` 在两份文件 SHA-256 相同时直接拒绝。目的是防止用同一份文件自己核对自己,但两个系统合法导出完全相同的内容时也会被拒绝。

**方案:** 同一路径仍然拒绝。内容相同时,默认拒绝并说明原因;用户确认两份文件确实来自不同系统后,可以加 `--allow-identical-content` 继续。报告会记录内容相同和这项确认。**放在 0.1.1。**

### 问题 2:无法证明文件真实、完整

完整性由用户用 `--source-complete` 和 `--destination-complete` 声明,工具不做核实。声明错了,也可能得到已验证。这是离线核对的根本限制,只靠代码无法完全解决。

**方案:**

1. **可以交叉核对的数字:** 新增 `--source-count N` 和 `--destination-count N`,填写在原系统里看到的总数,行数不符就拒绝给出已验证。**0.2.0**
2. **报告写明声明:** 已验证结果写成“在你声明的前提下已验证”,并列出每项声明及其来源。HTML 报告把它放在最显眼的位置。**0.2.0**
3. **真正解决靠直接读取:** 只读连接器由工具自己读取数据,不再依赖用户声明。**0.7.0 以后**

这项限制写在 README 的“已知问题”里,直到连接器完成。

### 问题 3:数据处理简单,大文件内存占用高

只有精确比较;整份文件读入内存,也没有大小限制。实测峰值内存约为文件大小的 68 倍。

**方案:**

| 任务 | 版本 |
| --- | --- |
| 默认上限,比如 200 MB 或 100 万行,超出就明确拒绝,用 `--max-rows` 调整 | 0.1.1 |
| 只保留用到的列;已验证的记录在报告里只存摘要,用 `--details all` 才保留全部明细 | 0.2.0 |
| 显式比较规则:去空格、忽略大小写、只比数字;日期按用户指定的格式解析后比较 | 0.2.0 |
| 目标文件改为逐行建索引,不再整份读入 | 0.2.0 |
| 大文件性能测试纳入 CI,100 万行峰值内存目标在 500 MB 以内 | 0.2.0 |

所有规则都必须显式选择,默认仍为精确比较。

### 问题 4:不检查目标中多出的记录

现在以来源为中心逐条查找,目标里多出的记录不会被发现。这是设计上的方向性,但需要支持“两边必须一致”的场景。

**方案:** 新增 `--scope`:

| 取值 | 含义 |
| --- | --- |
| `source`(默认) | 与现在相同,只检查来源里的记录 |
| `exact` | 目标中不应有来源外的记录。只有在声明目标完整时,多出的记录才判为不一致;否则只列出,不下结论 |

报告新增“只在目标中”一类,并单独计数。**放在 0.2.0。**

## 4. 版本计划

估时按每周 3–5 小时计算,都是粗估。

### 0.1.1 修补和打基础(约 6 小时,目标 11 月)

| 任务 | 位置 |
| --- | --- |
| 列名可以包含冒号,通过映射文件指定 | `offline/flowassert_offline/cli.py` |
| 内容相同的文件:默认拒绝,确认后可继续(问题 1) | 同上 |
| 文件大小和行数上限(问题 3) | 同上 |

| 建立共享的一致性测试样例,为以后移植到浏览器做准备 | `offline/conformance/*.json` |
| 写“导出 CSV 并完成第一次核对”的中英文教程 | `docs/guides/` |

验收:新用户照着教程 10 分钟内能跑通自己的文件;CI 覆盖 3.9、3.11、3.14;超过上限时给出明确的拒绝原因。

### 0.2.0 配置、比较规则和可信度(约 30 小时,目标 12–1 月)

| 任务 | 说明 |
| --- | --- |
| 配置文件 `flowassert.json` | 写好键、字段和规则,不用每次输入长命令 |
| 显式比较规则 | 精确(默认)、去首尾空格、忽略大小写、只比较数字。每个字段单独选择 |
| 报告记录规则 | 同时保存原值和处理后的值,写明用了哪条规则 |
| 文件编码 | `--encoding` 支持 UTF-8、UTF-16、GB18030,方便 Excel 和中文用户 |
| 报告格式版本 | JSON 增加 `schema_version`,写格式文档 `docs/report-format.md` |
| HTML 报告 | 一个独立的 HTML 文件,不懂代码的人也能看 |
| 总数交叉核对和声明说明 | `--source-count`、`--destination-count`,报告列出每项声明(问题 2) |
| 内存优化 | 只保留用到的列、精简报告、逐行建索引(问题 3) |
| 双向核对 | `--scope exact` 和“只在目标中”一类(问题 4) |

验收:每条规则都有正反两类测试;同样的输入和规则一定得到同样的结果;默认行为与 0.1 完全相同;100 万行峰值内存在 500 MB 以内。

### 0.3.0 浏览器内核对(约 30–40 小时,目标 2–3 月)

这是最重要的一版:让不会用命令行的人也能直接用。

| 任务 | 说明 |
| --- | --- |
| 把 Evaluator v2 移植到 TypeScript | 放在 `ui/src/offline/` |
| 一致性测试 | Python 和 TypeScript 跑同一组样例,结果必须完全相同 |
| 新页面“CSV 核对” | 选择两个文件、对应列、选规则,在浏览器里直接得出结果,复用现有的四状态和证据组件 |
| 导出报告 | 导出与命令行格式相同的 JSON 和 HTML |
| 在线演示 | 部署到 GitHub Pages,附示例文件 |

验收:

- 核对过程不发出任何网络请求,文件不离开电脑,并由浏览器测试证明。
- 两种实现的一致性测试全部通过。
- 中英文和手机宽度都能用。
- 在线演示里,依赖 Service 的页面明确标注“仅本地可用”。

| 任务 | 说明 |
| --- | --- |
| 结果解释 | “这个结果是什么意思”,只根据报告内容说明 |

| 反馈 | 试用反馈表单和页面上的“提交反馈”链接 |

### 0.7.0 及以后:视反馈决定

先看试用反馈。有人反馈,就先解决他们遇到的问题;只有前面的版本有真实用户在用,才继续下面的工作:

- **Service v2:** 在新的接口版本中接受用户自己的数据,冻结的 v1 保持不变。如果浏览器版已经够用,这一项可以取消。
- **只读连接器:** 先接 Google Sheets,再接 HubSpot 测试账号。开始前要完成[验证计划](product-dev/final-version/S1_VALIDATION_PLAN.md)里的检查。注册账号需要家长参与,并先确认服务条款的年龄要求。

## 5. 1.0 的条件

- 至少 3 位外部用户在用,并有他们的反馈记录
- 报告格式稳定,并承诺兼容
- 浏览器版和命令行版的一致性测试长期通过
- 至少一个只读连接器在测试账号上验证过,完整性不再只靠用户声明
- 文档完整,有一次第三方或社区的代码审查

## 8. 风险和对策

| 风险 | 对策 |
| --- | --- |
| Python 和浏览器两套实现结果不一致 | 共享一致性测试,不一致就不发布 |
| 功能越做越多 | 每个版本只做一个主题;新想法先记成 Issue |
| 文案夸大能力 | 发布前检查:每个说法都要有代码或测试支持 |
| 真实数据泄露 | 浏览器内处理、不上传;示例只用合成数据 |
| 过度依赖 AI 写代码 | 每个改动你都要能解释清楚,并有测试 |
| 坚持不下去 | 小步发布;可以随时暂停,并在 README 写明状态 |
